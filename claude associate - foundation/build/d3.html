Domain 3 · Product and Model Selection

12% · 1 bài nền tảng + 4 bài · ~65 phút

Domain 3 chiếm 12% đề, khoảng 7 trên 60 câu.

Cả domain xoay quanh một câu: việc này cần tính năng nào, model nào, và thứ gì phải được giữ lại sau khi chat kết thúc?

Đọc bài Nền tảng trước. Cuối mỗi bài có “Khi đi thi”: chọn đáp án trước rồi mới xem giải thích.

Nền tảng

Bản đồ app Claude: nơi dùng, gói, tính năng, model và context window

~14 phút

Người dùng Claude giỏi đã quyết xong vài chuyện trước khi gõ prompt. Khóa “Claude Platform & Model Foundations” trong lộ trình ôn Associate gọi đó là bốn quyết định: entry point (dùng Claude ở đâu), capability features (bật tính năng nào), model (chọn model nào) và context (Claude được thấy những gì). Bài này dựng từng thứ từ con số 0, theo thứ tự: nơi dùng → gói → tính năng → model → context window → một tuần làm việc thật chạy qua cả bốn quyết định.

1. Claude dùng ở đâu

Định nghĩa
App Claude
Ứng dụng chat của Anthropic, có ba bản: web (claude.ai), desktop và mobile. Đề Associate hỏi về app này, không hỏi API hay code.
Tài khoản
Một tài khoản dùng được trên cả ba bản. Help center ghi claude.ai, Claude Desktop và Claude Code cùng trừ vào một hạn mức dùng.
  • Phần lớn tính năng có ở cả ba bản, nhưng có vài chỗ khác. Bắt đầu Research trên mobile thì Claude chỉ tìm web, không dùng connector (phần nối Claude với app khác như Google Drive). Đổi quyền chia sẻ artifact (sản phẩm Claude làm ra, mở cạnh khung chat) phải làm trên web hoặc desktop, không làm trên mobile.
  • Ngoài app chat còn Claude in Chrome, Claude trong Excel và PowerPoint (gói trả phí), và Cowork (Claude làm việc nhiều bước trên file thật). Guide không nêu tên mấy thứ này, chỉ cần biết là có.

2. Gói: tính năng nào mở, dùng được bao nhiêu

Định nghĩa
Gói (plan)
Mức tài khoản: Free, Pro, Max, Team, Enterprise (còn có Ultra, guide không nhắc). Gói quyết định tính năng nào mở, model nào có, và hạn mức lớn cỡ nào.
Hạn mức dùng (usage limit)
Lượng việc bạn được nhờ Claude trong một khoảng thời gian, tính chung trên mọi chat. Gói trả phí có hạn mức theo phiên 5 giờ và theo tuần (bài 3.4).

4. Model là gì

Định nghĩa
Model
Bộ máy sinh ra câu trả lời. Cùng một câu hỏi, model khác nhau trả lời sâu khác nhau, nhanh chậm khác nhau, và trừ hạn mức nhiều ít khác nhau.
Model picker
Menu chọn model trong khung chat. Đổi model giữa chừng được; model mới áp từ câu trả lời kế tiếp.

Guide gọi tên ba tầng: Haiku (nhỏ, nhanh, nhẹ hạn mức), Sonnet (cân bằng, dùng hằng ngày), Opus (mạnh nhất trong ba, chậm và tốn hơn). Gói Free có Haiku và Sonnet; Opus từ Pro trở lên. App hiện có thêm Fable ở trên Opus. Bài 3.2 so ba tầng, bài 3.3 dạy cách chọn.

5. Context window là gì

Định nghĩa
Token
Mẩu chữ nhỏ mà model đọc và viết. Một từ có thể là một hay vài token. Độ dài chat, file, hạn mức đều đo bằng token.
Context window
Toàn bộ những gì Claude thấy được trong một chat tại một lúc, đo bằng token. Hình dung nó là mặt bàn làm việc: thứ gì nằm trên bàn thì Claude dùng được, thứ gì ở ngoài thì Claude không biết.

Trên mặt bàn có:

  • Tin nhắn của bạn và câu trả lời của Claude từ đầu chat.
  • File đính kèm, project instructions, project knowledge (hoặc phần knowledge được tìm ra khi Project dùng RAG).
  • Kết quả web search, connector, tool (công cụ Claude tự gọi, như tìm web hay chạy code). Help center gọi tool và connector là “token-intensive” (tốn nhiều token).
  • Instructions for Claude (lời dặn cấp tài khoản, áp cho mọi chat của bạn) và những gì memory nạp vào.

Ba điều cần nắm ngay:

  • Claude chỉ biết những gì nằm trên bàn. Chat khác, file chưa đưa vào, lời sửa ở chat tuần trước: Claude không tự thấy. Thứ chắc chắn đi theo sang chat mới chỉ là thứ đã được lưu (Project, instructions, memory). Gói trả phí còn có chat search: Claude tìm lại chat cũ khi bạn nhờ.
  • Kích thước cố định theo model. Model mới nhất (Haiku 5.5, Sonnet 5.5, Opus 5.5, Fable 5.1) có 1M token trong chat ở gói trả phí. Docs API quy đổi 1M token khoảng 555 nghìn từ tiếng Anh. Model không có tên trong danh sách thì mặc định 200K. Help center không ghi số cho gói Free.
  • Nâng gói không làm bàn to ra. Gói cho thêm hạn mức dùng. Context window vẫn là của model.

Tự kiểm tra

Câu hỏi viết bằng tiếng Anh như đề thật. Bấm vào câu hỏi để xem nghĩa và đáp án.

1. A Free-plan user asks why “Research” is missing from the “+” menu. What is the most likely reason? Nghĩa: một người dùng gói Free hỏi vì sao trong menu “+” không có “Research”. Lý do nhiều khả năng nhất là gì? Đáp: Research chỉ có ở gói trả phí (Pro, Max, Ultra, Team, Enterprise). Không phải lỗi cài đặt.
2. You turn off “Code execution and file creation” to keep things simple. Which features stop working? Nghĩa: bạn tắt “Code execution and file creation” cho gọn. Những tính năng nào ngừng chạy? Đáp: artifact, Skills, đọc file XLSX, và việc Claude tự tóm tắt chat dài trên gói trả phí. Tất cả đều cần cài đặt này.
3. Yesterday you corrected Claude’s tone in a chat. Today you open a new chat outside any project. Will Claude apply yesterday’s correction? Nghĩa: hôm qua bạn sửa giọng văn của Claude trong một chat. Hôm nay bạn mở chat mới, không thuộc Project nào. Claude có áp lời sửa hôm qua không? Đáp: chỉ khi lời sửa đó đã được lưu: vào memory, Instructions for Claude, hoặc một Project. Context của chat hôm qua không tự sang chat mới (trên gói trả phí, bạn có thể nhờ Claude tìm lại chat cũ, nhưng phải nhờ). Muốn chắc chắn thì tự lưu nó.
Nhớ nhanh
  • Bốn quyết định trước prompt: dùng ở đâu, tính năng nào, model nào, context gồm gì.
  • Free: Haiku, Sonnet, tối đa 5 Project, không có Research. Opus và Research từ gói trả phí.
  • Code execution (“Create and edit files”) là nền của artifact, Skills và tự tóm tắt chat dài.
  • Context window = mặt bàn của một chat. Cố định theo model; nâng gói không làm nó to ra.

Bắt đầu từ chat, chỉ đổi khi chat thiếu một thứ

Chat làm được rất nhiều việc. Chỉ đổi sang tính năng khác khi việc cần một thứ chat không có. Ba thứ hay thiếu:

  • Lặp lại. Tuần nào cũng dán lại cùng tài liệu, cùng lời dặn → Project.
  • Nhiều nguồn. Phải tìm, so sánh, dẫn nguồn từ nhiều nơi → Research.
  • Giữ lâu. Kết quả là một sản phẩm sẽ sửa tiếp, dùng lại, gửi người khác → artifact.

Project: khi việc lặp lại trên cùng tài liệu

  • Tài liệu trong project knowledge và lời dặn trong project instructions áp cho mọi chat trong Project.
  • Các chat trong cùng Project không thấy nội dung của nhau. Thứ mọi chat cần phải nằm trong knowledge.
  • Free tạo được tối đa 5 Project. Gói trả phí có RAG: khi tài liệu gần chạm giới hạn context, Claude tự chuyển sang tìm phần liên quan, chứa được tới gấp 10 lần.
  • Team và Enterprise chia sẻ được Project với hai mức quyền. Can view (được xem): xem nội dung, knowledge, instructions và chat với Project, không sửa. Can edit (được sửa): sửa instructions, knowledge, quản lý thành viên. Chia sẻ Project không chia sẻ các chat bên trong.
  • Cả nhóm cần cùng tài liệu thì dùng một Project chia sẻ. Gửi file qua email hay chuyển tiếp đoạn chat tạo ra nhiều bản sao, và bản nào cũng sẽ cũ.
  • Viết instructions, chọn tài liệu cho Project là chuyện của bài 5.1. Bài này chỉ hỏi: lúc nào thì dùng Project.

Artifact: khi kết quả là sản phẩm để dùng tiếp

  • Claude tạo artifact khi nội dung đáng kể, đứng riêng được, thường trên 15 dòng, và nhiều khả năng bạn sẽ sửa hoặc dùng lại. Ngắn hay mang tính trò chuyện thì Claude trả lời ngay trong chat.
  • Sửa bằng cách nhờ Claude, sửa trực tiếp với các mẫu Docs, Slides, Design, hoặc bôi đen một đoạn rồi chọn “Edit with Claude” (sửa cùng Claude).
  • Mọi artifact lưu ở tab Artifacts trong thanh bên, mở lại được từ bất kỳ chat nào.
  • Sửa một tin nhắn cũ tạo ra một nhánh chat riêng, có artifact riêng. Bản cũ không mất.
  • Xuất file: Docs ra Word, PDF, Markdown, Google Docs. Slides ra PowerPoint, PDF, Google Slides.
  • Artifact mới tạo là riêng tư. Muốn người khác mở được thì chỉnh quyền chia sẻ.
  • Cần bật code execution (“Create and edit files”). Chọn artifact, trả lời ngay trong chat hay dữ liệu có cấu trúc cho từng người đọc là chuyện của bài 2.6.
Tình huống. Chị Hạnh, trưởng nhóm pháp chế, sáng thứ Hai nào cũng mở chat mới, dán ba mẫu hợp đồng, bộ quy tắc văn phong tám trang, rồi dặn lại “giọng trang trọng, theo luật Việt Nam”. Có tuần chị quên dán bộ quy tắc, bản nháp ra sai thuật ngữ. Đồng nghiệp xin “cái prompt của chị” qua email, mỗi người giữ một bản khác nhau. Vấn đề không nằm ở prompt. Đây là việc lặp lại trên cùng bộ tài liệu, nên chỗ của nó là một Project chia sẻ: tài liệu vào knowledge, lời dặn vào instructions, chị giữ quyền sửa, cả nhóm được xem.
Tệ
  • Dán lại cùng tài liệu, cùng lời dặn mỗi tuần.
  • Gửi đoạn chat hay file qua email cho cả nhóm.
  • Bật Research để “đọc lại” tài liệu nội bộ đã có sẵn.
  • Chép bản brief từ chat sang Word rồi sửa tay mỗi lần.
Tốt
  • Project: tài liệu trong knowledge, lời dặn trong instructions.
  • Project chia sẻ: người sửa có Can edit, cả nhóm có Can view.
  • Research cho câu hỏi cần tìm và so nhiều nguồn.
  • Brief làm thành artifact, sửa ở khung bên, xuất Word khi xong.
Bẫy: đáp án có một người lặp đi lặp lại một bước làm tay (dán lại tài liệu, chuyển tiếp đoạn chat, chép từ chat sang file) thường là đáp án sai. Đáp án đúng bỏ bước lặp đó bằng đúng tính năng.

Khi đi thi

Bài này thường ra 2 dạng câu hỏi. Đọc đề, chọn một đáp án trước; phần giải thích chỉ hiện ra sau khi bạn chọn.

Dạng 1: việc lặp lại trên cùng bộ tài liệu
Đề sẽ viết kiểu này
“Every Monday, an HR coordinator opens a new chat, pastes the same 12-page onboarding policy and a paragraph of tone guidance, then asks Claude to draft welcome emails for that week’s new hires. Some weeks she forgets the tone paragraph and the drafts come out too casual. What is the most appropriate change?” Dịch: Mỗi thứ Hai, một nhân viên điều phối nhân sự mở chat mới, dán cùng bản chính sách hội nhập 12 trang và một đoạn dặn về giọng văn, rồi nhờ Claude soạn email chào mừng nhân viên mới của tuần. Có tuần chị quên dán đoạn dặn giọng văn và bản nháp ra quá suồng sã. Thay đổi phù hợp nhất là gì?
Bạn chọn đáp án nào?

Phân tích đề
  • Đề kể: cùng một tài liệu, cùng một lời dặn, dán lại mỗi tuần.
  • Chỗ khó: lỗi xảy ra những tuần người làm quên dán. Gốc của lỗi là một bước làm tay lặp lại, không phải prompt kém.
  • Đề hỏi: thay đổi nào làm việc lặp lại này chạy ổn định.
Cần biết để chọn
  1. Project knowledge và project instructions áp cho mọi chat trong Project. Không phải dán lại.
  2. Một chat kéo dài cả năm sẽ chạm giới hạn độ dài hoặc bị tự tóm tắt, chi tiết cũ bị nén (bài 3.4).
  3. Research đi tìm và tổng hợp nhiều nguồn. Nó không giữ tài liệu cho lần sau.
  4. Memory ghi các ý ngắn về bạn theo chủ đề, không phải chỗ giữ nguyên văn một văn bản 12 trang.
Từng đáp án
  • A sai. Hấp dẫn vì “không phải dán lại”, nhưng chat cứ dài thêm mỗi tuần, tới lúc chạm giới hạn hoặc bị tóm tắt, và lời dặn từ tháng đầu có thể bị nén mất (ý 2). Đổi một rủi ro lấy rủi ro khác.
  • B sai. Ở đây không có gì phải đi tìm: tài liệu đã nằm sẵn trong tay (ý 3). Bật Research mỗi tuần vừa tốn hạn mức vừa vẫn phải đưa lại tài liệu.
  • C đúng. Tài liệu và lời dặn được đặt một lần, mọi chat trong Project đều thấy (ý 1). Không còn bước dán tay để mà quên.
  • D sai. Memory có thể nhớ “email nên ấm áp”, nhưng không giữ nguyên văn bản chính sách mà email phải bám vào (ý 4).
Dạng 2: câu hỏi cần nhiều nguồn, có dẫn nguồn
Đề sẽ viết kiểu này
“A product marketer on a Pro plan must brief leadership tomorrow on how five competitors priced their latest releases. She wants a cited comparison that draws on public web sources and on the team’s notes in a connected Google Drive. Which approach is most appropriate?” Dịch: Một nhân viên marketing sản phẩm dùng gói Pro, ngày mai phải báo cáo lãnh đạo về cách năm đối thủ định giá sản phẩm mới nhất của họ. Chị muốn một bản so sánh có dẫn nguồn, lấy từ các nguồn web công khai và từ ghi chú của nhóm trong Google Drive đã kết nối. Cách nào phù hợp nhất?
Bạn chọn đáp án nào?

Phân tích đề
  • Đề kể: năm đối thủ, sản phẩm mới nhất, cần dẫn nguồn, nguồn nằm cả trên web lẫn trong Drive.
  • Chỗ khó: thông tin mới, có thể ra sau thời điểm kiến thức của model. Nhiều nguồn, hai loại nguồn. Và người làm lo chuyện hạn mức.
  • Đề hỏi: cách tiếp cận phù hợp nhất cho một cuộc tìm hiểu nhiều nguồn.
Cần biết để chọn
  1. Research chạy nhiều lượt tìm nối tiếp, trên web và công cụ đã kết nối như Google Workspace. Cần gói trả phí và bật web search.
  2. Research luôn chạy trên Opus 5.5 (dự phòng Opus 4.8), bất kể model đang chọn trong chat.
  3. Bắt đầu Research trên mobile thì Claude chỉ tìm web, không dùng connector.
  4. Kiến thức của model dừng ở một thời điểm. Giá “mới nhất” phải đi tìm, không dựa vào trí nhớ của model.
Từng đáp án
  • A đúng. Đúng loại việc của Research: nhiều nguồn, hai loại nguồn, cần dẫn nguồn (ý 1). Bắt đầu từ web hoặc desktop để Research dùng được connector Drive (ý 3).
  • B sai. Phải tự tay đi chụp từng trang, ảnh chụp đứng yên và sẽ cũ, còn ghi chú trong Drive thì bị bỏ ngoài. Project hợp với tài liệu dùng lại nhiều lần, không phải một cuộc điều tra một lần.
  • C sai. Không tìm thì không có nguồn để dẫn, và giá của bản phát hành mới có thể ra sau thời điểm kiến thức của model (ý 4).
  • D sai. Hấp dẫn vì nghe tiết kiệm, nhưng Research không chạy trên model bạn chọn trong chat (ý 2). Đổi sang Haiku không đổi được gì.
Biết thêm
  • Guide v1.0 gọi là “research mode”. App hiện tại gọi là Research (nút “+” → Research). Khi thi chọn theo guide: “research mode” chính là Research.
  • Research dùng connector mà không hỏi duyệt từng lần. Nhưng nó không dùng được MCP server cục bộ (máy chủ kết nối công cụ chạy trên chính máy bạn) cấu hình trong bản Desktop.
  • Team, Enterprise: admin tắt cả Opus 5.5 lẫn Opus 4.8 cho vai trò của bạn thì Research không chạy.
  • Trong giao diện Claude mới, web search không còn nút bật tắt. Claude tự tìm khi thấy cần.
  • Tên và mô tả của Project không hiện cho Claude. Muốn Claude biết điều gì thì viết vào instructions hoặc knowledge.
  • Artifact có thể tự gọi Claude bên trong (“Artifacts that use Claude”, trước gọi là AI-powered artifacts). Người xem đăng nhập bằng tài khoản Claude của mình, hạn mức trừ vào gói của người xem, người tạo không trả gì.
Quy tắc: bắt đầu bằng chat. Lặp lại trên cùng tài liệu thì Project, cần tìm và dẫn nhiều nguồn thì Research, sản phẩm sẽ sửa, dùng lại, chia sẻ thì artifact.
Nhớ nhanh
  • Ba thứ chat thiếu: lặp lại (Project), nhiều nguồn (Research), giữ lâu (artifact).
  • Research: gói trả phí, cần web search, luôn chạy Opus 5.5. Cần connector thì bắt đầu trên web hoặc desktop.
  • Project: knowledge và instructions áp cho mọi chat. Các chat không thấy nhau. Chia sẻ có Can view, Can edit.
  • Artifact: thường trên 15 dòng, lưu ở tab Artifacts, cần bật code execution.

Người dùng app không trả tiền theo token; họ tiêu hạn mức. Giá API chỉ cho thấy chênh lệch: mỗi token Opus đắt gấp đôi Sonnet, còn Haiku rẻ hơn nhiều lần. Haiku và Sonnet dùng ít token hơn; Opus suy nghĩ nhiều hơn nên tiêu nhiều token hơn.

Cái giống nhau không giúp bạn chọn

  • Cùng thông số giới hạn. Haiku 5.5, Sonnet 5.5, Opus 5.5 cùng có context window 1M token, cùng trả lời tối đa 128K token, cùng kiến thức tới tháng 6/2026, cùng nhận chữ và ảnh, cùng dùng tool (công cụ như tìm web).
  • Vậy “Opus đọc được nhiều hơn” hay “Haiku có context nhỏ hơn” đều sai. Ngược lại, “context như nhau nên tầng nào cũng như nhau” cũng sai. Thông số giới hạn chỉ cho biết bàn rộng cỡ nào, không cho biết người làm giỏi cỡ nào.
  • Không có tầng chuyên ngành. Docs mô tả các tầng theo độ khó, tốc độ và lượng việc, không theo lĩnh vực. Không có “model cho tài chính” hay “model cho marketing”. Chữ “analysis” (phân tích) trong danh sách thế mạnh của Sonnet là một loại việc, không phải một ngành.

Khoảng cách lộ ra ở việc khó

  • Việc đơn giản (tóm tắt email, phân loại, trích ngày tháng): ba tầng thường cho kết quả gần như nhau. Hướng dẫn chọn model của Anthropic viết: “Using Opus on a task Haiku could handle costs you tokens for no gain and slows you down in the process” (dùng Opus cho việc Haiku làm được là tốn token mà không được gì, lại còn chậm hơn).
  • Việc khó (nhiều bước, lập luận dài, nhiều nguồn mâu thuẫn, chưa có cách làm sẵn): khác biệt giữa các tầng mới hiện ra.
  • Muốn so hai tầng, thử trên phần khó nhất của việc. Đem 50 email dễ ra thử thì tầng nào cũng giống nhau, và bạn sẽ kết luận sai rằng tầng cao không hơn gì.
  • Hai câu tự hỏi để đặt việc vào tầng: việc có nhiều bước không? Có phải lập luận qua nhiều nguồn, nhiều ràng buộc không? Mỗi câu “có” kéo lên một tầng.

Hạn mức: tầng nặng tiêu nhanh hơn

  • Cùng một lượng việc, tầng nặng trừ hạn mức nhanh hơn. Chạy cả việc dễ lẫn việc khó trên Opus thì hạn mức cạn sớm.
  • Hướng dẫn của Anthropic cho người dùng app: chưa chắc thì Sonnet. Việc đơn giản, cần ngay thì Haiku. Đã thử Sonnet mà vẫn chật vật thì lên Opus.
  • Hết hạn mức giữa tuần vì việc dễ chạy trên Opus: chuyển việc dễ xuống Haiku, giữ Opus cho việc khó. Mở chat mới không giúp, vì hạn mức dùng tính chung trên mọi chat (bài 3.4).
Tình huống. Anh Quân ở phòng kế toán dùng Opus cho mọi việc, kể cả đổi định dạng ngày tháng trong 400 dòng Excel và gắn nhãn hóa đơn. Tới thứ Tư anh hết hạn mức tuần, đúng hôm cần phân tích chênh lệch giữa ba bản dự toán. Đồng nghiệp đề nghị chuyển hết sang Haiku “vì model nào cũng đọc được 1M token”. Cách đầu đốt hạn mức vào việc không cần lập luận sâu. Cách sau giao việc khó nhất cho tầng nhẹ nhất. Đúng ra: việc dễ, nhiều thì Haiku; phân tích dự toán thì Opus.
Tệ
  • Dùng Opus cho mọi việc “cho chắc”.
  • Chọn tầng theo ngành: “Opus cho tài chính”.
  • Nghĩ context như nhau thì tầng nào cũng như nhau.
  • So hai tầng trên việc dễ rồi kết luận tầng cao không hơn gì.
Tốt
  • Việc đơn giản, nhiều, cần nhanh: Haiku. Chưa chắc: Sonnet. Sonnet chật vật: Opus.
  • Chọn theo độ khó và tốc độ cần, không theo ngành.
  • Biết thông số giới hạn giống nhau, năng lực thì không.
  • So tầng trên phần khó nhất của việc.

Phân tích đề
  • Đề kể: 30 hợp đồng, so chéo, tìm mâu thuẫn, đề xuất. Pháp chế sẽ làm theo.
  • Chỗ khó: lập luận của đồng nghiệp đúng một nửa. Context window đúng là như nhau. Cái sai là kết luận rút ra từ đó.
  • Đề hỏi: đáp lại đúng nhất, tức là vừa đúng tầng vừa đúng lý do.
Cần biết để chọn
  1. Haiku 5.5, Sonnet 5.5, Opus 5.5 cùng có context 1M token và cùng trả lời tối đa 128K token. Các thông số này không phân biệt được tầng.
  2. Các tầng khác nhau ở độ sâu lập luận, tốc độ và hạn mức. Việc nhiều bước, nhiều nguồn mâu thuẫn, sai thì tốn kém: tầng cao.
  3. Điểm tin cậy Claude tự chấm không phải bằng chứng đúng sai (câu mẫu 1).
Từng đáp án
  • A sai. Gắn năng lực vào kích thước context (ý 1). Window chỉ là bàn rộng cỡ nào, không phải người làm giỏi cỡ nào.
  • B sai. Vẫn là Claude chấm Claude (ý 3). Một mâu thuẫn bị bỏ sót sẽ không hiện ra để mà bị chấm điểm thấp.
  • C sai. Kết luận đúng nhưng lý do sai: cả ba tầng cùng trần 128K token đầu ra (ý 1). Kiểu đáp án “đúng tầng, sai lý do” này dễ làm người ôn vội chọn nhầm.
  • D đúng. Chỉ đúng chỗ sai trong lập luận (ý 1) và chọn tầng theo độ khó, mức rủi ro (ý 2).

Phân tích đề
  • Đề kể: một người hỏi model “chuyên tài chính” để viết giải thích chênh lệch ngân sách.
  • Chỗ khó: câu hỏi đã gài sẵn một giả định sai: có model chuyên ngành. Ba đáp án nhận giả định đó, mỗi đáp án một tầng.
  • Đề hỏi: hướng dẫn chính xác nhất, tức là sửa giả định trước khi chọn.
Cần biết để chọn
  1. Docs mô tả các tầng theo độ khó, tốc độ và lượng việc. Không tầng nào được mô tả là chuyên một ngành.
  2. Hướng dẫn chọn model của Anthropic cho người dùng app: chưa chắc thì bắt đầu với Sonnet; Sonnet chật vật thì lên Opus.
  3. Giải thích vì sao ngân sách lệch là việc lập luận (nêu nguyên nhân, so sánh), không chỉ chép số.
Từng đáp án
  • A sai. Không tầng nào được huấn luyện riêng cho tài chính (ý 1). Opus mạnh hơn ở việc khó nói chung, không phải ở một ngành.
  • B đúng. Sửa giả định sai (ý 1), rồi đưa ra cách chọn đúng: theo đặc điểm của việc, xuất phát từ Sonnet (ý 2).
  • C sai. “Analysis” là một loại việc, không phải một ngành (ý 1). Sonnet có thể là lựa chọn ổn ở đây, nhưng vì lý do khác hẳn.
  • D sai. Giải thích chênh lệch cần lập luận (ý 3). Và chọn Haiku vì “ngành này toàn số” vẫn là chọn theo ngành.

TS 3.3

Chọn model theo việc: cân chi phí, tốc độ và chất lượng

~13 phút

Cần biết trước: ba tầng Haiku, Sonnet, Opus ở bài 3.2.

Khái niệm của bài
Chi phí (cost)
Trong app là hạn mức bị trừ. Trên API, và trên Enterprise tính theo lượng dùng, là tiền trả theo token.
Tốc độ (speed)
Bao lâu thì có câu trả lời. Quan trọng khi khách đang chờ, hoặc khi cả lô việc phải xong trước một giờ nhất định.
Chất lượng (quality)
Đúng, đủ, đủ sâu cho người dùng kết quả. Cái giá của một kết quả sai quyết định cần bao nhiêu chất lượng.
Effort (mức nỗ lực)
Cài đặt trong model picker quyết định Claude suy nghĩ kỹ đến đâu: Low, Medium, High, Extra high, Max. Mức cao hơn kỹ hơn, chậm hơn, tốn hơn.
Chi phí cho một việc xong
Tổng hạn mức (hoặc tiền) để ra một kết quả dùng được, tính cả lần chạy lại và thời gian sửa tay. Khác với giá mỗi token.

Bốn câu hỏi trước khi chọn

  1. Việc khó cỡ nào? Nhiều bước, lập luận dài, nhiều nguồn mâu thuẫn thì lên tầng.
  2. Cần nhanh cỡ nào? Khách đang chờ, có hạn chót sát thì nghiêng về tầng nhanh.
  3. Làm bao nhiêu lần? Hàng trăm, hàng nghìn lần thì từng chút hạn mức cộng lại thành nhiều.
  4. Sai thì mất gì? Bản nháp nội bộ sai thì sửa. Nhận xét ảnh hưởng điểm học sinh, con số trong hợp đồng sai thì hậu quả thật, và cần người duyệt (bài 2.4).

Câu 4 thường quyết định. Cùng là “viết nhận xét”, nhận xét cho bản nháp nội bộ và nhận xét đi kèm điểm số đòi hai mức chất lượng khác nhau.

Lời giải guide nói dùng model mạnh nhất cho mọi việc là phí “cost and latency budget” (ngân sách chi phí và thời gian chờ). Phân tích đầy đủ ở bài ôn 3 câu mẫu.

Hai cách này lấy từ trang chọn model trong docs API. Với một việc lẻ trong app mà chưa biết chọn gì, hướng dẫn cho người dùng app chỉ một câu: bắt đầu với Sonnet.

Lô việc lẫn lộn: tách theo độ khó

Ví dụ: 3.000 phản hồi khách sau một sự kiện, cần gắn nhãn theo sáu chủ đề trước sáng mai. Khoảng 5% là khiếu nại dài, nhiều ý, khó xếp loại.

  • Dồn hết lên Opus: chậm, hạn mức cạn nhanh, có thể không xong kịp. 95% phản hồi không cần tới mức lập luận đó.
  • Dồn hết xuống Haiku: nhanh và nhẹ, nhưng đúng 5% ca khó dễ bị xếp sai.
  • Tách ra: Haiku cho phần lớn, các ca dài hoặc được đánh dấu “không chắc” chuyển sang Sonnet hay Opus. Rồi kiểm ngẫu nhiên vài mẫu ở cả hai nhóm.

Docs API gọi đây là kết hợp model: một model rẻ làm phần lớn, khi gặp quyết định khó thì chuyển cho một model mạnh hơn.

Thử trên việc thật trước khi đổi tầng

  • Docs viết: “Having a good evaluation set is the most important step in the process” (có một bộ bài kiểm tốt là bước quan trọng nhất), và “Test with your actual prompts and data” (thử bằng prompt và dữ liệu thật của bạn).
  • So các tầng ở độ chính xác, chất lượng, cách xử lý ca khó. Rồi mới cân với chi phí.
  • Trong app: chạy cùng một đầu vào thật trên hai model, so mỗi bản với yêu cầu của việc, ghi lại mất bao lâu để sửa.
  • So chi phí cho một việc xong, không so giá mỗi token. Tầng rẻ mà phải chạy lại ba lần hoặc sửa tay nửa tiếng thì chưa chắc rẻ.
  • Không tính là thử:
    • Đổi luôn rồi chờ người dùng phàn nàn.
    • Hỏi Claude “Haiku có làm được không?”.
    • Cắt ngắn sản phẩm cho vừa sức model nhẹ.

Chỉnh effort trước, đổi tầng sau

Docs API: “Tuning effort is often a better lever than switching models” (chỉnh effort thường là đòn bẩy tốt hơn đổi model). Mức effort mặc định hợp với phần lớn việc; mức cao nhất để dành cho việc khó nhất.

Khi đi thi

Bài này thường ra 2 dạng câu hỏi. Đọc đề, chọn một đáp án trước; phần giải thích chỉ hiện ra sau khi bạn chọn.

Dạng 1: lô việc lẫn lộn, có hạn chót
Đề sẽ viết kiểu này
“Each night, an operations team must tag about 6,000 support tickets by category before a 7 a.m. stand-up. Most tickets are routine, but roughly 3% are long, ambiguous complaints that need judgement. Which approach best balances cost, speed and quality?” Dịch: Mỗi đêm, đội vận hành phải gắn nhãn phân loại cho khoảng 6.000 phiếu hỗ trợ trước buổi họp 7 giờ sáng. Phần lớn là phiếu thường gặp, nhưng khoảng 3% là khiếu nại dài, mơ hồ, cần cân nhắc. Cách nào cân bằng tốt nhất chi phí, tốc độ và chất lượng?
Bạn chọn đáp án nào?

Phân tích đề
  • Đề kể: 6.000 phiếu mỗi đêm, có giờ chót 7 giờ sáng. 97% thường gặp, 3% cần cân nhắc.
  • Chỗ khó: một lô mà hai loại việc. Bất kỳ đáp án nào dùng một model cho tất cả đều hy sinh một trong ba thứ.
  • Đề hỏi: cách cân bằng tốt nhất cả chi phí, tốc độ và chất lượng.
Cần biết để chọn
  1. Tầng nhẹ làm tốt việc đơn giản, nhiều, nhanh và ít hạn mức. Tầng mạnh để dành cho chỗ cần cân nhắc.
  2. Tốc độ cũng là một yêu cầu: lô lớn trên tầng chậm có thể trễ hạn, và tiêu hạn mức nhanh.
  3. Lô lẫn lộn thì tách theo độ khó, không bắt một model gánh tất cả.
  4. Lời Claude đoán về model nào hợp không thay được thử trên việc thật.
Từng đáp án
  • A đúng. Tách lô theo độ khó (ý 3): phần lớn chạy nhanh và nhẹ (ý 1, 2), 3% ca khó vẫn được cân nhắc đúng mức.
  • B sai. Hấp dẫn vì nghe chắc ăn về chất lượng, nhưng 97% phiếu không cần tới tầng mạnh. Chậm hơn, tốn hạn mức hơn, có thể không xong trước 7 giờ (ý 2). Cùng kiểu sai với đáp án A của câu mẫu 2.
  • C sai. Ngược lại: nhanh và rẻ, nhưng bỏ mặc đúng nhóm ca cần cân nhắc (ý 1, 3).
  • D sai. Lời đoán của Claude không phải thử nghiệm (ý 4), và vẫn ép một model làm cả lô lẫn lộn (ý 3).
Dạng 2: định đổi xuống tầng rẻ hơn, làm gì trước
Đề sẽ viết kiểu này
“A training coordinator uses Opus every week to turn workshop notes into a two-page summary that managers use to plan follow-up coaching. To save the team’s usage, her manager suggests moving the task to Sonnet. What should she do first?” Dịch: Một điều phối viên đào tạo tuần nào cũng dùng Opus để biến ghi chú buổi workshop thành bản tóm tắt hai trang; các quản lý dựa vào bản này để lên kế hoạch kèm cặp tiếp theo. Để tiết kiệm hạn mức của nhóm, quản lý đề nghị chuyển việc này sang Sonnet. Chị nên làm gì trước tiên?
Bạn chọn đáp án nào?

Phân tích đề
  • Đề kể: một việc lặp lại hằng tuần đang chạy tốt trên Opus. Có đề nghị chuyển xuống Sonnet để đỡ tốn.
  • Chỗ khó: các quản lý dựa vào bản tóm tắt để ra quyết định. Đổi mà hỏng thì người chịu là họ.
  • Đề hỏi: bước đầu tiên, tức là bước cho biết có nên đổi hay không.
Cần biết để chọn
  1. Docs: thử bằng prompt và dữ liệu thật; so độ chính xác, chất lượng, ca khó, rồi mới cân chi phí.
  2. So chi phí cho một việc xong: bản rẻ hơn mà phải sửa tay lâu thì chưa chắc tiết kiệm.
  3. Yêu cầu của sản phẩm do người dùng nó đặt ra, không phải do sức của model.
Từng đáp án
  • A sai. Đổi trước, kiểm sau. Người phát hiện lỗi lại chính là các quản lý đang dựa vào bản tóm tắt để lên kế hoạch.
  • B sai. Câu “được” của Claude nghe yên tâm nhưng không thử gì cả (ý 1). Lời đoán về một model khác không phải bằng chứng.
  • C sai. Cắt bớt sản phẩm cho vừa sức model là đổi yêu cầu của việc (ý 3). Các quản lý vẫn cần đủ thông tin.

Context có hạn: khi nào mở chat mới, khi nào tóm tắt, khi nào lưu lại

~14 phút

Cần biết trước: token, context window và bảng “context, Project, memory” ở bài Nền tảng.

Khái niệm của bài
Hạn mức dùng (usage limit)
Giới hạn tổng lượng dùng trên mọi chat theo thời gian. Gói trả phí có giới hạn theo phiên (reset đủ 5 giờ sau tin nhắn đầu tiên của phiên) và giới hạn theo tuần.
Giới hạn độ dài (length limit)
Giới hạn một chat dài được bao nhiêu. Do context window của model quyết định.
Tự quản lý context (automatic context management)
Trên gói trả phí có bật code execution, khi chat gần chạm giới hạn, Claude tự tóm tắt các tin nhắn cũ để chat tiếp.
Lưu lại (persist)
Đặt thông tin vào chỗ mà chat sau vẫn thấy: project knowledge, project instructions, Instructions for Claude (lời dặn cấp tài khoản, trước gọi là profile preferences), memory.
Memory
Claude ghi dần các ý về bạn thành từng chủ đề trong lúc chat, hoặc khi bạn bảo “nhớ cái này”, rồi dùng lại ở chat sau.
Chat ẩn danh (incognito chat)
Chat không lưu vào lịch sử, không ghi vào memory, không dùng memory cũ.

Context chứa gì, và vì sao nhiều hơn chưa chắc tốt hơn

  • Mỗi lần trả lời, Claude dựa trên mọi thứ đang nằm trong context: tin nhắn cũ, file, instructions, knowledge, kết quả tool và connector.
  • Claude không học từ lời sửa ở chat khác. Sửa ở chat tuần trước không làm model khá hơn ở chat tuần này. Chỉ thứ đã lưu mới đi theo.
  • Nhiều hơn chưa chắc tốt hơn. Bài viết kỹ thuật của Anthropic gọi hiện tượng này là “context rot” (context bị mục): “as the number of tokens in the context window increases, the model’s ability to accurately recall information from that context decreases” (token trong context càng nhiều, khả năng nhớ chính xác thông tin trong đó càng giảm).
  • Tool và connector tốn nhiều token. Một chat có năm connector đang bật, ba bản nháp bỏ dở và hai file PDF không dùng nữa thì phần việc chính bị lẫn giữa đống thứ thừa.

Dọn context:

  • Gỡ file không dùng nữa khỏi chat hoặc Project.
  • Tắt connector và web search khi việc không cần.
  • Giữ project instructions ngắn, vì chúng nằm trong mọi chat.
  • Hạ effort khi không cần suy nghĩ sâu.
  • Mở chat mới cho việc không liên quan.

  • Rủi ro: bản tóm tắt nén chi tiết. Một con số hay một ràng buộc chốt từ đầu có thể bị nén mất, trong khi câu trả lời vẫn đọc rất trôi chảy và trông như đầy đủ.

  • Mở chat mới khi chưa lưu những gì đã chốt.
  • Tuần nào cũng gõ lại cùng một lời sửa.

  • Chat đã dài thì nhắc lại con số, ràng buộc quan trọng.
  • Gặp giới hạn độ dài thì chat mới hoặc Project, chia nhỏ đầu vào.
  • Lưu quyết định ra Project trước khi rời chat.
  • Lời sửa lặp lại thì đưa vào instructions.

Khi đi thi

Bài này thường ra 2 dạng câu hỏi. Đọc đề, chọn một đáp án trước; phần giải thích chỉ hiện ra sau khi bạn chọn.

Dạng 1: giới hạn độ dài hay hạn mức dùng
Đề sẽ viết kiểu này
“A Pro-plan user has been working in one long chat and now pastes in a 250-page interview transcript. Claude responds that the message would exceed the length limit for this chat. She plans to upgrade to Max so that the chat can hold the transcript. What is the most appropriate next step?” Dịch: Một người dùng gói Pro đang làm việc trong một chat dài, giờ dán vào bản ghi phỏng vấn 250 trang. Claude báo tin nhắn sẽ vượt giới hạn độ dài của chat này. Chị định nâng lên gói Max để chat chứa được bản ghi. Bước tiếp theo phù hợp nhất là gì?
Bạn chọn đáp án nào?

Phân tích đề
  • Đề kể: một chat đã dài, thêm một bản ghi 250 trang, Claude báo vượt giới hạn độ dài.
  • Chỗ khó: đề có hai loại giới hạn, và người dùng đang chữa nhầm loại. Thông báo nói “độ dài của chat này”, không nói “hết hạn mức”.
  • Đề hỏi: bước tiếp theo phù hợp nhất.
Cần biết để chọn
  1. Giới hạn độ dài là của một chat, do context window của model quyết định. Help center: không tăng được kích thước context window cố định của gói.
  2. Hạn mức dùng (phiên 5 giờ, tuần) là chuyện khác. Chờ reset hay nâng gói chỉ chữa hạn mức dùng.
  3. Help center chỉ cách xử lý giới hạn độ dài: mở chat mới, hoặc dùng Project.
  4. Haiku 5.5, Sonnet 5.5, Opus 5.5 cùng có context 1M token.
Từng đáp án
  • A sai. Nhầm hai loại giới hạn (ý 1, 2). Nâng gói cho thêm hạn mức dùng, không làm context window to ra. Hấp dẫn vì “trả thêm tiền thì được nhiều hơn” nghe hợp lý.
  • B đúng. Đúng cách help center chỉ (ý 3). Chat mới không kéo theo phần lịch sử dài đang chiếm chỗ; chia nhỏ hoặc chỉ đưa đoạn cần thì vừa context hơn.
  • C sai. Reset 5 giờ là của hạn mức dùng (ý 2). Chờ xong, chat cũ vẫn đầy như vậy.
  • D sai. Cùng context 1M token (ý 4). Đổi sang Haiku không cho chat thêm chỗ.
Dạng 2: chat dài quên điều đã chốt
Đề sẽ viết kiểu này
“An events coordinator has used one chat for four weeks to plan a conference. Claude’s newest schedule ignores two constraints agreed in week one: the venue holds 180 people, and nothing can be scheduled on Friday. What is the most appropriate next step?” Dịch: Một điều phối viên sự kiện đã dùng một chat suốt bốn tuần để lên kế hoạch hội thảo. Lịch mới nhất của Claude bỏ qua hai ràng buộc đã chốt từ tuần đầu: hội trường chứa 180 người, và không xếp gì vào thứ Sáu. Bước tiếp theo phù hợp nhất là gì?
Bạn chọn đáp án nào?

Phân tích đề
  • Đề kể: một chat bốn tuần. Hai ràng buộc chốt từ tuần đầu giờ bị bỏ qua.
  • Chỗ khó: Claude không “cãi” ràng buộc, nó không còn thấy rõ chúng. Chat dài đã được tóm tắt, chi tiết đầu chat bị nén.
  • Đề hỏi: bước tiếp theo phù hợp nhất, tức là cách sửa tận gốc chứ không chỉ sửa lịch lần này.
Cần biết để chọn
  1. Chat dài trên gói trả phí được tự tóm tắt. Chi tiết đầu chat có thể bị nén mất, trong khi câu trả lời vẫn trôi chảy.
  2. Thứ phải đúng suốt cả việc nên được lưu ra ngoài chat (project knowledge, instructions). Chat mới trong Project thấy ngay.
  3. Xóa một chat không xóa các memory đã ghi từ chat đó.
  4. Nhờ Claude tóm tắt cả bốn tuần trong chính chat đó là nhờ nó dựa vào đúng phần lịch sử đang bị nén.
Từng đáp án
  • A sai. Vá triệu chứng. Viết hoa có thể sửa được lượt này, nhưng chat vẫn dài thêm và chuyện cũ sẽ lặp lại (ý 1).
  • B sai. Hấp dẫn vì nghe như “tóm tắt rồi đi tiếp”. Nhưng bản tóm tắt dựa trên lịch sử đã bị nén (ý 4), dài, tốn chỗ, và có thể sót đúng hai ràng buộc đang thiếu. Thiếu bước tự liệt kê và kiểm.
  • C đúng. Tự liệt kê thứ phải giữ, lưu ở chỗ mọi chat sau đều thấy (ý 2). Chat mới nhẹ, không kéo theo bốn tuần nháp cũ.
  • D sai. Xóa chat không xóa memory (ý 3), và còn bỏ luôn bốn tuần công sức mà chưa lưu lại quyết định nào.

  • Team, Enterprise: Owner không xem được memory của thành viên. Owner tắt memory cho cả tổ chức là xóa vĩnh viễn memory của mọi người.
Quy tắc: việc mới thì chat mới, việc cũ quá dài thì tóm tắt rồi tự kiểm, thứ phải dùng lại thì lưu vào Project hoặc memory trước khi rời chat.
Nhớ nhanh
  • Hạn mức dùng (mọi chat, reset theo phiên và tuần) khác giới hạn độ dài (một chat, do context window). Nâng gói không làm context to ra.
  • Chat dài được tự tóm tắt (gói trả phí, bật code execution): lịch sử giữ nguyên, chi tiết có thể bị nén.
  • Lời sửa lặp lại là dấu hiệu phải lưu. Mở chat mới chỉ an toàn khi thứ quan trọng đã được lưu.
  • Xóa chat không xóa memory. Chat ẩn danh không có trong Project; ở đó thì tắt Memory trong “+” trước tin đầu.

  • Bốn quyết định trước prompt: dùng Claude ở đâu, bật tính năng nào, chọn model nào, context gồm những gì.

Tên và con số phải thuộc

  • Research: chỉ gói trả phí (Pro, Max, Ultra, Team, Enterprise). Cần bật web search. Bật ở “+” → Research. Luôn chạy Opus 5.5 (dự phòng Opus 4.8). Guide gọi là “research mode”.
  • Projects: Free tối đa 5. RAG chỉ gói trả phí, chứa tới gấp 10 lần. Chia sẻ trên Team, Enterprise với Can view, Can edit. Chia sẻ Project không chia sẻ chat.
  • Artifact: thường trên 15 dòng, đứng riêng, sẽ dùng lại. Lưu ở tab Artifacts. Mới tạo là riêng tư. Cần code execution.
  • Code execution: “Code execution and file creation”, giao diện mới là “Create and edit files”, ở Settings → Capabilities. Nền của artifact, Skills, đọc XLSX, tự tóm tắt chat dài.
  • Skills: thư mục hướng dẫn, script, tài nguyên. Claude chỉ nạp khi cần. Mọi gói. Tải lên ở Customize → Skills.
  • Model: Haiku nhanh nhất, nhẹ nhất. Sonnet cân bằng, mặc định khi chưa chắc. Opus mạnh nhất trong ba, từ Pro. Giá API mỗi 1M token vào / ra: Haiku từ $0.10 / $0.50, Sonnet $2 / $10, Opus $4 / $20 (Fable $10 / $50). Cùng 1M context, 128K đầu ra.
  • Effort: Low, Medium, High, Extra high, Max.
  • Context: 1M token cho các model mới nhất (chat gói trả phí). 200K cho model không có tên trong danh sách. 1M token khoảng 555 nghìn từ tiếng Anh.
  • Hạn mức: phiên reset 5 giờ sau tin nhắn đầu. Tuần reset vào mốc cố định. Xem ở Settings → Usage.
  • Memory: bật sẵn Free, Pro, Max, Ultra. Team, Enterprise do Owner bật, từng người tự bật. Chat search: gói trả phí. Chat ẩn danh: mọi gói, không có trong Project, giữ 30 ngày.
  • File: 20 file mỗi chat. File Project tối đa 30MB. PDF trên 100 trang chỉ đọc chữ.
