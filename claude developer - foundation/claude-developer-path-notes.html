        Core 1

        AI Capabilities and Limitations

        Khoảng 60 phút. Vì sao model hành xử như vậy: dự đoán token, kiến thức, trí nhớ làm việc, khả năng điều khiển.

        Domain 5Domain 6Domain 8

        AI không giỏi đều, cũng không kém đều. Nó mạnh hay yếu theo 4 thuộc tính. Mỗi thuộc tính là một dải từ “làm tốt” đến “dễ hỏng”. Việc của bạn là xác định task nằm ở đâu trên từng dải, rồi kiểm tra và bổ sung cho phù hợp. Ranh giới sẽ dịch chuyển khi model tốt lên, nhưng 4 thuộc tính thì giữ nguyên.

        Model có “tính cách” từ đâu

        • Pretraining: đọc lượng văn bản khổng lồ và học đoán chữ tiếp theo. Kết quả là một cỗ máy viết tiếp văn bản, chưa biết khái niệm “giúp người dùng”.
        • Fine-tuning: dựa trên đánh giá của con người, model học coi input là một yêu cầu, trả lời giúp ích, từ chối yêu cầu có hại.
        • Fine-tuning để lại 4 dấu vân tay: sycophancy (dễ đồng ý với tiền đề sai), verbosity (mặc định dài), over-caution (thận trọng quá mức), loose calibration (độ tự tin không khớp độ chính xác).

        Next Token Prediction

        • Model giống autocomplete cực kỳ tinh vi hơn là công cụ tìm kiếm. Cùng một cơ chế tạo ra cả sự trôi chảy lẫn hallucination.
        • Chỗ hay bịa nhất là chi tiết cụ thể: tên, ngày, số liệu, trích dẫn, URL. Càng cụ thể càng phải kiểm tra.
        • Cách khắc phục: trích dẫn nguồn, để model báo khi không chắc, giới hạn đầu ra, pattern generator-verifier.
        • Sampling: model tính phân phối xác suất cho token tiếp theo rồi chọn một token. Temperature thấp thì tập trung, cao thì ngẫu nhiên. Top-k giữ k lựa chọn cao nhất. Top-p giữ nhóm nhỏ nhất có tổng xác suất đạt p, và tự co giãn theo độ tự tin của model.

        Knowledge

        • Kiến thức đóng băng tại knowledge cutoff. Câu hỏi đúng là “chủ đề này xuất hiện nhiều đến mức nào trong dữ liệu huấn luyện”.
        • Lỗi đặc trưng: thông tin cũ, độ phủ không đều, thiên kiến kế thừa, không nhớ nguồn.
        • Cách khắc phục: web search, RAG, MCP, tool use.
        • Embedding: biến text thành vector độ dài cố định (ví dụ 1.024 chiều). Text gần nghĩa thì vector gần nhau. Retrieval là lấy k tài liệu gần câu hỏi nhất, thường đo bằng cosine similarity.

        Working Memory

        • Context window có kích thước cố định. Đây là vách đá, không phải dốc thoải: chạy tốt cho đến khi bỗng hỏng, thường bị cắt bớt âm thầm.
        • Model không học từ việc bạn sửa nó. Phiên mới là bắt đầu từ con số 0.
        • Lost in the middle: model nhớ tốt phần đầu và phần cuối, phần giữa dễ bị bỏ sót (đường cong chữ U). Đặt chỉ dẫn quan trọng ở đầu và nhắc lại ở cuối. Nhiều context hơn không có nghĩa là tốt hơn.
        • Cách khắc phục: memory, compaction, project, context lớn hơn, workflow nhiều agent.

        Steerability

        • Model làm theo chỉ dẫn bằng cách viết tiếp pattern, không phải vì hiểu ý bạn.
        • Lỗi đặc trưng: reasoning drift (lỗi nhỏ cộng dồn qua nhiều bước) và letter over spirit (đúng câu chữ, sai ý định).
        • Cách khắc phục: system prompt, code execution, cho model hiển thị suy luận, structured output.
        • Khi model làm đúng chữ mà vô dụng: nêu rõ mục tiêu, đừng lặp lại chỉ dẫn mạnh hơn.

        Core 2

        AI Fluency for Builders

        Khoảng 45 phút. Các quyết định của người build sản phẩm: giao việc, mô tả, đánh giá, chịu trách nhiệm.

        Domain 4Domain 7

        4D Framework

        • Delegation: việc nào giao cho AI, việc nào giữ lại.
        • Description: nói rõ bạn cần gì và muốn AI làm theo cách nào.
        • Discernment: đánh giá output trước khi dùng.
        • Diligence: chịu trách nhiệm hoàn toàn về kết quả, bất kể AI đóng góp bao nhiêu.

        Description và Discernment là vòng trong (tương tác hằng ngày). Delegation và Diligence là vòng ngoài (quyết định lớn).

        Bộ công cụ của builder

        EmpathyDesignArchitectureImplementationJudgmentShipping
        AI yếuVừaVừaMạnhYếuVừa

        Giao phần implementation thì an toàn, giao phần judgment thì không. Viết acceptance test trước khi viết code để bạn và AI có chung định nghĩa “xong”.

        Ba chế độ hợp tác: Automation (AI làm, bạn kiểm tra), Augmentation (cùng làm), Agency (AI tự hành trong giới hạn bạn đặt).

        Description Chain

        Tiếng nói người dùng → requirement → technical spec → chỉ dẫn cho AI → test. Prompt engineering chỉ là một mắt xích. Test là dạng mô tả chính xác nhất. Code chạy mà sản phẩm hỏng là lỗi mô tả ở mắt xích phía trước.

        5 lăng kính đánh giá

        1. Functional integrity: chạy đúng với dữ liệu thật, không chỉ dữ liệu test.
        2. Production readiness: chịu tải, không race condition.
        3. Problem fit: giải quyết đúng nhu cầu thật, không chỉ đúng spec chữ.
        4. Experience quality: người dùng làm được việc mà không cần hướng dẫn.
        5. Responsible impact: minh bạch vai trò của AI, không bỏ sót nhóm người dùng.

        Điểm mù hay gặp của AI: concurrency, security, và lỗi chỉ xuất hiện khi lên quy mô. AI cũng không tự nhắc về migration, versioning, rate limit, feature flag, trừ khi bạn hỏi.

        UX: bốn nguyên tắc clarity, hierarchy, accessibility, feedback. “Làm cho đẹp” là mong muốn, không phải spec. AI không tự làm đúng accessibility, phải yêu cầu rồi kiểm tra.

        Có nên dựng Project? Hỏi ba câu: task có lặp lại, context có ổn định, format có cố định. Đúng từ 2 câu trở lên thì dựng.

        Bốn lớp năng lực

        • Project mang context.
        • Skill định nghĩa quy trình lặp lại.
        • Code Execution kiểm chứng tính toán. Model sinh chữ chỉ tạo con số “nghe hợp lý”. Con số nào sẽ được dùng thật, dữ liệu cần làm sạch, biểu đồ, file thật (xlsx, pptx…) thì dùng code execution.
        • Memory giữ liên tục giữa các phiên. Memory theo phạm vi Project nên khách hàng A không lẫn sang khách hàng B. Incognito giữ phiên khỏi memory và lịch sử.

        Chọn model

        • Haiku: việc có cấu trúc, khối lượng lớn (phân loại 500 hợp đồng theo rubric rõ ràng).
        • Sonnet: điểm khởi đầu cho hầu hết việc chuyên môn.
        • Opus: phán đoán phức tạp, input mơ hồ, rủi ro cao.

        Khi context suy giảm

        Dấu hiệu: model bỏ qua chỉ dẫn đã làm đúng trước đó, chỉ phản hồi lượt gần nhất. Ba cách xử lý: Restart, Summarize rồi mở phiên mới kèm tóm tắt, Persist vào Memory hoặc knowledge base.

        Bẫy hay gặp: nhắc lại chỉ dẫn trong một phiên đã suy giảm là sai, nâng lên model mạnh hơn cũng sai. Đáp án đúng là mở phiên mới mang theo bản tóm tắt.

        Role 5

        Claude Platform 101

        Khoảng 90 phút. Từ API call đầu tiên đến agent loop, tool use, thinking, built-in tools, skills, MCP, context management và managed agents. Khóa quan trọng nhất cho đề.

        Domain 2Domain 5Domain 8Domain 1

        1. Ba lớp của Platform

        • Primitives: Messages API, tool use, files, web search, code execution, MCP, skills.
        • Infrastructure: managed agents, retry, queue, observability.
        • Controls: dashboard, eval.

        Tóm gọn: build bằng primitives, scale bằng infrastructure, vận hành bằng controls.

        2. Cấu trúc request

        • Bắt buộc: model, max_tokens, messages. Tùy chọn: system để định vai trò.
        • response.content là mảng block, không phải chuỗi. Lặp qua và kiểm tra type: text, tool_use, thinking…
        • API key để trong .env, không hardcode.
        import Anthropic from "@anthropic-ai/sdk";
const client = new Anthropic();
const res = await client.messages.create({
  model: "claude-sonnet-5-5",
  max_tokens: 1024,
  system: "You are a terse senior code reviewer.",
  messages: [{ role: "user", content: "Review this code: ..." }],
});
for (const block of res.content) {
  if (block.type === "text") console.log(block.text);
}

        3. Chọn model theo eval

        • Lấy 20–30 ví dụ thật làm bộ eval. Chạy từ Haiku, chưa đạt thì Sonnet, cần mới lên Opus. Model đúng là model rẻ nhất mà output vẫn đủ tốt để ship.
        • response.usage trả về input và output token, là căn cứ tính tiền.
        • Production: route từng loại task sang model khác nhau trong cùng endpoint (Haiku phân loại, Sonnet viết nháp, Opus xử lý việc khó).

        4. Agent loop

        1. Gửi messages kèm tools.
        2. Nếu stop_reason là tool_use: chạy tool.
        3. Đẩy toàn bộ response.content vào messages với role assistant.
        4. Đẩy kết quả với role user, dạng block tool_result có tool_use_id trùng id lệnh gọi.
        5. Lặp đến khi stop_reason là end_turn.
        while (true) {
  const res = await client.messages.create({ model, max_tokens: 1024, tools, messages });
  if (res.stop_reason !== "tool_use") break;
  messages.push({ role: "assistant", content: res.content });
  messages.push({
    role: "user",
    content: res.content
      .filter(b => b.type === "tool_use")
      .map(b => ({ type: "tool_result", tool_use_id: b.id, content: runTool(b.name, b.input) })),
  });
}

        Bạn sở hữu vòng lặp và tool. Claude sở hữu phần suy luận.

        5. Tool use

        • Claude không tự chạy tool, code của bạn chạy.
        • Định nghĩa: name, description, input_schema (JSON Schema), truyền qua mảng tools.
        • Description mơ hồ là lý do số một khiến agent gọi sai hoặc không gọi tool.
        • Nhiều tool thì dispatch theo name. Claude có thể gọi nhiều tool trong cùng một lượt.
        • Tool runner (SDK TypeScript, Python, Ruby): tự sinh schema từ function và tự chạy vòng lặp. TS dùng client.beta.messages.toolRunner(...) rồi runner.untilDone().

        6. Thinking

        • Adaptive thinking: thinking: { type: "adaptive" }, model tự quyết định khi nào và nghĩ bao nhiêu.
        • Độ sâu chỉnh bằng effort đặt trong output_config, không đặt cạnh khối thinking. Mức: low, medium, high, xhigh, max. Mặc định tùy model.
        • Nên dùng: toán, logic nhiều bước, debug, so sánh đánh đổi. Không nên: phân loại, trích xuất, boilerplate.
        • Suy luận hiển thị trong response dưới dạng thinking block.

        7. Built-in tools

        A. API trong production (Domain 2, 5)

        • Realtime hay Batch: việc khối lượng lớn, không cần kết quả ngay (chạy qua đêm, báo cáo định kỳ) thì dùng Message Batches API: xử lý bất đồng bộ trong cửa sổ 24 giờ với chi phí thấp hơn. Gọi song song nhiều request đồng bộ không làm giảm giá mỗi token. Đây là câu mẫu số 1 trong guide.
        • Streaming: dùng khi người dùng cần thấy chữ chạy ra dần hoặc response dài. Phải xử lý trường hợp stream bị ngắt giữa chừng: ghi nhận phần đã nhận, quyết định gửi lại hay báo lỗi rõ ràng.
        • Lỗi và retry: phân biệt lỗi nên retry (rate limit 429, quá tải hoặc lỗi phía server 5xx/529) với lỗi không nên retry (request sai 400, sai xác thực 401, thiếu quyền 403). Retry dùng exponential backoff có jitter và tôn trọng header retry-after. SDK chính thức đã có sẵn cơ chế retry mặc định, cấu hình được.
        • Vision và PDF: gửi ảnh hoặc tài liệu dưới dạng content block trong messages, cùng request với câu hỏi.
        • Gọi qua nhà cung cấp thứ ba: Claude có trên Amazon Bedrock, Google Cloud (Vertex AI), Microsoft Foundry và Claude Platform on AWS. Model ID, cách xác thực và một số tính năng có thể khác so với API trực tiếp, cần đọc docs của từng nền tảng.
        • Ghim phiên bản model: mỗi model ID là một snapshot cố định. Production nên ghim ID cụ thể, nâng cấp có chủ đích sau khi chạy eval, vì bản mới có thể có thay đổi phá vỡ (breaking changes).
        • Version prompt: quản lý prompt như code: lưu trong repo hoặc config có version, review khi đổi, chạy lại eval trước khi deploy.
        • Theo dõi chi phí: đọc usage trong mỗi response để log input/output token. Prompt caching: đánh dấu phần đầu ổn định của request bằng cache_control; phần được cache phải là tiền tố giống hệt nhau giữa các lần gọi (tools, system, rồi messages), nên phần thay đổi luôn đặt sau cùng.
        • Fast mode: tốc độ output cao hơn với giá cao hơn, chỉ có trên một số model.
        • Claude hiểu chỉ dẫn khác nhau theo giao diện: claude.ai có system prompt và tính năng riêng; API thì stateless, chỉ có những gì bạn gửi; Claude Code đọc thêm CLAUDE.md và settings.

        B. Prompt engineering và output handling (Domain 6)

        • Chỉ dẫn rõ ràng, cụ thể: nói rõ mục tiêu, đối tượng, định dạng, giới hạn. Đừng để model tự đoán.
        • System hay user: vai trò, quy tắc bền vững, giọng văn đặt ở system prompt. Dữ liệu và yêu cầu cụ thể của từng lượt đặt ở user message.
        • XML tag để tách từng phần: <instructions>, <document>, <example>. Tài liệu dài đặt trước, câu hỏi đặt cuối.
        • Zero-shot, single-shot, multi-shot: thêm ví dụ khi cần định dạng hoặc phong cách nhất quán. Ví dụ nên đa dạng để model không bắt chước một mẫu duy nhất.
        • Tinh chỉnh lặp: sửa prompt dựa trên bộ ví dụ cố định, đo bằng eval, không sửa theo cảm giác từ một lần chạy.
        • Làm sạch input: dữ liệu người dùng bọc trong tag riêng, giới hạn độ dài, loại bỏ nội dung không cần.
        • Structured output: dùng tính năng structured outputs hoặc định nghĩa schema qua tool để có JSON đúng cấu trúc. Dù vậy backend vẫn phải validate (ví dụ bằng Zod hoặc JSON Schema).
        • Parse phòng thủ: bỏ markdown fence trước khi parse, bọc JSON.parse trong try/catch, nếu sai thì gửi lại kèm thông báo lỗi để model sửa, giới hạn số lần thử.
        • Hoài nghi output tự tin: giọng chắc chắn không có nghĩa là đúng. Con số, trích dẫn, ID phải được kiểm tra với nguồn thật.

        C. Security (Domain 7)

        • Prompt injection: mọi nội dung lấy từ bên ngoài (web, file, email, kết quả tool) là dữ liệu không tin cậy. Tách khỏi chỉ dẫn tin cậy, không cho nội dung đó kích hoạt hành động nhạy cảm. Đây là câu mẫu số 2: tăng temperature, xin người dùng đừng chèn lệnh, hay đổi model lớn hơn đều không phải biện pháp.
        • Nhiều lớp guardrail: validate input, giới hạn tool, kiểm tra output, hook chặn hành động phá hủy, người duyệt cho hành động không thể hoàn tác.
        • Least privilege: agent chỉ có đúng quyền cần thiết. Tool đọc tách khỏi tool ghi. MCP chỉ bật tool cần dùng.
        • PII và rò rỉ dữ liệu: chỉ gửi dữ liệu cần thiết, che hoặc lược PII khi có thể, không log dữ liệu nhạy cảm, không đưa secret vào prompt.
        • Secrets và API key: lưu trong biến môi trường hoặc secret manager, không commit vào repo, tách key theo môi trường dev/staging/production, xoay vòng định kỳ, theo dõi usage bất thường.
        • Xác thực và phân quyền: hành động agent thực hiện thay người dùng phải kiểm tra quyền của chính người dùng đó ở backend, không dựa vào lời model.

        D. Eval và debug (Domain 4)

        • Bộ eval là định nghĩa của “xong”: tập input đại diện kèm tiêu chí chấm. Chạy lại mỗi khi đổi prompt, model hoặc tool.
        • Nhận diện loại lỗi: lỗi HTTP/API (xác thực, rate limit, request sai) khác hẳn lỗi output (sai format, sai nội dung, bịa).
        • Tách lỗi tầng tích hợp với lỗi model: log request và response thô. Nếu request gửi đi đã thiếu context hoặc sai cấu trúc thì lỗi ở code của bạn; nếu request đúng mà output sai thì xem lại prompt, model, tool description.
        • Trace analysis: với agent, ghi lại từng lượt: tool nào được gọi, input gì, kết quả gì, stop_reason gì. Đọc trace để biết agent hỏng ở bước nào.

        E. Kiến trúc agent (Domain 1)

        • Workflow hay agent: các bước biết trước, cần ổn định và dễ kiểm soát thì dùng workflow (chaining, routing, chạy song song). Task mở, không đoán trước được số bước thì dùng agent. Mặc định chọn giải pháp đơn giản nhất chạy được.
        • Manager/supervisor: một agent điều phối giao việc cho các agent chuyên trách, mỗi agent có context riêng, rồi tổng hợp kết quả.
        • Human-in-the-loop: đặt điểm dừng chờ người duyệt trước hành động không thể hoàn tác (xóa, chuyển tiền, gửi ra ngoài).
        • Framework: Claude Agent SDK, hoặc các framework như Strands, LangGraph, PydanticAI giúp trừu tượng hóa agent loop. Tự viết loop cho toàn quyền kiểm soát; managed agents khi muốn Anthropic host vòng lặp.

        F. Nền tảng kỹ thuật (Domain 2, 5)

        • SDK là lớp bọc REST API: hiểu request/response JSON bên dưới giúp debug khi SDK báo lỗi.
        • Async và concurrency: gọi song song có giới hạn để không chạm rate limit, dùng hàng đợi cho tải lớn.
        • Websockets và streaming để đẩy kết quả realtime về client.
        • SDLC: đưa prompt, cấu hình và eval vào quy trình review và CI giống như code.

        G. MCP server (Domain 8)

        • Khi nào viết MCP server: khi muốn một năng lực (ví dụ API kho hàng nội bộ) được nhiều ứng dụng Claude dùng chung và bảo trì độc lập. Đây là câu mẫu số 3. Built-in tool không tự gọi được API nội bộ tùy ý.
        • Transport: stdio cho server chạy như tiến trình cục bộ cùng máy với client; kết nối mạng (HTTP, socket) cho server từ xa dùng chung.
        • Server cung cấp tools, resources, prompts; client kết nối và đưa danh sách đó cho model.
